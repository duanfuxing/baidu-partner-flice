# 新版单资质完整链路：真实采集结果

采集日期：2026-09-12。样本：当前输入公司的“推广审查 / 资质1”，同一卡片内 3 张图片。采集使用项目专用 Chrome，正式上传代码未修改；只在诊断脚本中增加监听和阶段标记。

## 结论

**已复现“百度实际保存成功，但程序报告保存超时”。这次失败并非文件未上传或保存接口未成功。**

3 次上传和 3 次保存均返回 HTTP 200、业务 `status=0`。第三次保存由页面在程序进入保存阶段前发出；程序随后才注册局部保存监听并调用 `handleSubmit`，页面因数据未变化而不再发送请求，程序等待 60 秒后报错。

之后在同一浏览器中重新进入详情、重新加载编辑页，并独立核对服务端详情返回值、3 个文件内容 SHA-256、文件顺序及举证链接，全部一致；页面显示“已保存待送审”。这是一例已确认的误报原因，不能据此排除其他运行中的弱网、服务端错误或预览故障。

## 一张资质卡实际经历的网络步骤

第一张文件前至程序报告超时的窗口共记录 39 个浏览器请求。以下次数仅指此窗口，排除初始化及后续独立核验。

| 接口 / 资源 | 次数 | 本次实际作用与依赖 |
| --- | --- | --- |
| POST `/permit/web/permit/savelicepic` | 3 | multipart 文件上传；返回文件 ID，尚不等于该文件已保存到业务资质 |
| POST `/permit/web/permit/getocrresultbyernielayout` | 1 | 第一张触发 OCR；`fileUrl` 使用上传返回 ID；返回的识别值随后进入保存字段 |
| GET `/permit/web/permit/getlicepic`，image | 9 | 页面预览及保存刷新后的预览加载 |
| GET `/permit/web/permit/getlicepic`，fetch | 9 | 当前程序主动下载预览文件进行哈希核验，不能误认为全部是页面原生请求 |
| GET `/permit/web/middle/index` | 3 | 每次保存前出现，带当前客户及认证上下文；请求顺序已确认，完整业务含义尚需进一步核实 |
| POST `/permit/web/permit/submitlice` | 3 | 保存当前卡片完整累积文件集合及表单数据 |
| GET `/permit/web/permit/geturlinfo` | 3 | 每次保存后重新读取详情；返回保存记录及文件关联 |
| GET `/permit/web/config/getliceaddinfo` | 3 | 每次保存后按资质类型重新读取附加字段配置 |
| 其他图片资源 | 5 | 辅助显示资源，路径已匿名化；不作为资质保存成功依据 |

本次观察到的主顺序为：

```text
选择文件
  → savelicepic 返回文件 ID
  → 第一张出现 OCR 请求；页面预览与程序内容核验
  → 页面保存前检查（middle/index）
  → submitlice 保存累积文件和表单
  → geturlinfo 重新读取详情
  → getliceaddinfo 读取附加配置、页面重建预览
  → 核对文件与举证、等待稳定
  → 下一张文件
```

不同支路可能重叠，不能把此顺序实现为固定延时后点击。

## 三张文件的实测时序

时间相对于“第一张文件处理开始”标记；耗时为采集环境中的请求完整结束时间，包含监听及路由环境影响。

| 文件 | 上传请求 | 上传开始 / 耗时 | 保存请求 | 保存开始 / 耗时 | 保存文件集合 |
| --- | --- | --- | --- | --- | --- |
| 1 | r197 | 2.036 秒 / 586 ms | r203 | 7.315 秒 / 215 ms | 文件 1 |
| 2 | r208 | 13.270 秒 / 447 ms | r214 | 19.038 秒 / 1082 ms | 文件 1、2 |
| 3 | r222 | 26.635 秒 / 334 ms | r228 | 30.520 秒 / 485 ms | 文件 1、2、3 |

第三张的关键证据：

1. 29.963 秒，当前卡片记录到鼠标移出事件。
2. 30.272 秒，页面发出保存前的 `middle/index`。
3. 30.520 秒，页面发出 r228 `submitlice`；约 31.005 秒完整返回成功，包含全部 3 个文件及正确举证链接。
4. 31.645 秒，程序才进入 `_save_qualification_card`。它的局部监听未覆盖已经完成的 r228。
5. 当前页面 `handleSubmit` 包含 `JSON.stringify(t.value) === Fe.value` 时直接返回的分支；保存成功后会更新 `Fe.value`。因此再次调用不保证产生新请求。
6. 后续没有新的 `submitlice`；91.948 秒，程序在 `src/new_audit_qualification.py:944` 抛出“已调用页面保存方法，但未发出保存请求”错误。

卡片实际 `onMouseleave` 方法包含 300 ms 定时器，在页面有焦点等条件满足时调用保存方法。该源码与本次事件顺序一致，支持“页面自动保存先于程序局部监听”的判断。仅凭 trusted 鼠标事件不能区分人工鼠标与 Playwright 引起的事件，本次未进一步断言鼠标移出的具体物理来源。

## 上传、创建和更新的参数传递

- 上传响应 `savelicepic.data` → OCR 的 `fileUrl`、预览查询的 `filename`、保存请求的 `upload_file`。
- `upload_file` 是当前卡片全部文件 ID 的逗号连接集合；本次依次为 1、2、3 个文件，后续保存不是仅提交新文件。
- 第一次 `submitlice` 返回的记录标识，出现在详情及后续保存的 `lice_index`。
- 第一次保存后的 `geturlinfo` 返回 `licemap_id`，后续保存请求携带该关联标识。
- 第一次和后续保存的 `manage_type` 不同；附加字段 `addInfos` 的形状也发生变化。不能将首次请求原样重放用于更新。
- 虽然程序只填写文件和举证链接，真实页面仍会携带 `licename`、`liceserial`、`liceid`、`tradeid`、附加字段等。本次 OCR 返回值与保存中的名称、编号字段一致。
- `geturlinfo` / `geturlandproductinfo` 的资质记录提供已保存的 `filename`、`evidence_url`、`lice_index`、`licemap_id`，可作为恢复时的独立核对来源。只读读取能力已观察到，但尚未实现正式恢复机制。

## 持久化验证与附带发现

重新读取业务列表后，`trade_lice_info.count` 从 0 变为 1。r245 的记录中，文件集合及举证与本次输入一致。随后读取实际观察到的预览 URL，3 个文件的 SHA-256 均与本地输入一致；编辑页重新加载后也显示 3 个已就绪文件、正确举证及“已保存待送审”。

另外捕获到两个前置/读取异常：

- 初始 URL 列表查询在页面行业参数初始化时出现不同参数请求，其中一个返回 `1011`，后续程序查询发生网络失败。诊断脚本在同一浏览器中等待初始化后重新查询，成功进入详情；正式导航代码未修改。
- 保存后首次重新进入编辑页的 `geturlinfo` 返回 HTTP 200、`status=1009`，导致编辑表单未出现；在同一页执行一次只读重新加载后恢复。尚未验证该业务码的具体语义，不归因为文件保存失败。

## 页面操作还是接口提交

| 方式 | 本次证据支持的判断 |
| --- | --- |
| 继续页面操作 | 页面能完成上传与保存；但失焦、鼠标移出、布局变化、自动保存与主动保存存在竞态。当前“每次调用保存都等一个新响应”的假设已被证伪 |
| 调用页面暴露的保存方法 | 能复用页面校验和动态参数，但仍有脏检查、前置检查、自动保存及回填；不能当作必定发送 HTTP 的纯函数 |
| 直接调用上传和草稿保存接口 | 已识别主要请求和标识传递，具备继续验证的基础；尚未实际执行脱离页面的写入实验，不能宣称可完整替代。必须区分创建/更新并处理结果未知、认证变化及并发自动保存 |

建议优先让监听覆盖单张文件的完整生命周期，关联所有来源的成功保存，并在结果不明确时读取已保存详情。**先修正成功判定，再独立验证接口方案**，才能比较两者可靠性，而不是把本次程序误报算作页面上传能力不足。

## 限制与当前状态

- 仅一张主资质卡、3 张图片；没有验证 PDF、补充卡、多业务、跨公司、服务端限流或所有异常情形。
- 使用项目当前“主动调用页面方法”的上传模式；未另做纯人工点击或直接接口写入对照实验。
- 采集器每 250 ms 记录页面状态变化；路由保护禁用浏览器 HTTP 缓存，因此请求量与延时不能直接外推到普通用户浏览器。
- Chromium 在 multipart 观测中省略了文件正文。历史事件中的 `bytes: 0` 表示未取得二进制，不代表上传空文件；实际本地大小及哈希见 `capture_config`，持久化哈希见 `verification.json`。采集器后续已将其改名为 `captured_bytes` 并明确省略状态。
- 样本草稿保留在百度端。仅上传选定目录，没有删除已有业务；最终送审请求数为 0。正式上传、恢复和调度代码均未改变。

网络事件语义参考：[Playwright Request 文档](https://playwright.dev/python/docs/api/class-request)。本报告的具体接口行为、时间和结论来自上述真实采集文件。

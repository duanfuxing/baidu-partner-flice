# 任务 23：新版业务资质表单适配

## 状态

第三轮代码审查问题已修复并通过 120 项全量测试；等待真实页面最终联调。

## 目标

在新版 `/newaudit#/lice/invest_lice_list/...` 投放资质详情中进入“新增业务资质”，保留并处理默认“推广审查”业务，再按 `input.json` 为其余每个资质类型创建独立业务卡片并逐张上传文件。

## 已确认页面流程

1. 在“投放资质”详情页点击“新增资质”。
2. 在“新增投放资质”页面点击蓝色“新增业务资质”，不点击“新增产品资质（推荐）”。
3. 页面默认生成“业务1–4”：业务1为红色标签“推广审查”且不可删除；业务2–4为其他默认业务，可通过标签右侧 `×` 删除。
4. 从业务4向业务2删除默认多余业务，每次删除后重新扫描；最终先只保留业务1。
5. 每家公司输入必须且只能包含一个“推广审查”类型，先在业务1中上传该类型全部文件。
6. 对其余每个 `qualificationType`：点击一次蓝色“新增业务资质”，在新业务卡片的“经营业务”下拉框输入类型名查询，只选择显式映射后的唯一精确候选项。
7. 每个业务类型将全部实际文件按 `input.json` 顺序展开后逐张处理：第一张使用业务自带上传表单；第二张勾选“我还需要补充其他资质”生成“补充资质1”；第三张及后续逐次点击“新增补充资质”。
8. 补充资质类型保持页面默认“其它”；每个上传表单只上传一张文件，举证链接取该文件所属资质目录的 `evidenceUrl`。
9. 文件上传和非空举证链接失焦分别触发 `POST /permit/web/permit/submitlice`，必须逐次等待 HTTP 200 且响应 JSON `status == 0`。
10. 所有业务和文件完成并通过最终集合校验后，根据最终提交开关决定是否点击底部“发起审核”。
11. 点击“发起审核”后，在“确认发起审核？”弹窗中点击“确定”；等待 `https://fkzhunru.baidu.com/permit/web/permit/submitall`，仅 HTTP 200 且 JSON `status == 0` 视为最终成功。

## 输入映射

| 现有输入 | 新版页面 | 规则 |
| --- | --- | --- |
| `typeName == "推广审查"` | 默认业务1 | 必须存在且唯一；先处理，不新增业务 |
| 其他 `qualificationTypes[].typeName` | 新增业务卡片的“经营业务” | 每个类型新增一个业务，输入类型名查询并按显式映射精确选择 |
| `qualification.files[]` | 主资质或补充资质上传表单 | 展平为逐张文件；一个表单只上传一张 |
| 第一张实际文件 | 业务自带上传表单 | 不创建补充资质 |
| 第二张实际文件 | 补充资质1 | 勾选“我还需要补充其他资质”生成 |
| 第三张及后续文件 | 补充资质2..N | 逐次点击“新增补充资质”生成 |
| `qualification.evidenceUrl` | 当前文件表单的举证链接 | 同一资质目录的多张文件复用该目录举证链接 |
| 补充资质类型 | “其它” | 保持页面默认值，不根据资质名称修改 |
| 资质编号、资质名称、有效期 | 不操作 | 新版不填写、不回读、不校验；仅保留为输入记录及旧版流程数据 |

## 默认业务清理

- 删除发生在任何文件上传前，目标固定为默认业务2–4，保留不可删除的推广审查业务1。
- 从后向前删除，避免标签重编号造成误删。
- 每次点击 `×` 前读取当前业务内容，确认不是“推广审查”。
- 删除后重新扫描，最终必须只剩业务1且其经营业务为“推广审查”。
- 无法确认业务内容、业务1可删除状态异常或删除后目标仍存在时停止当前公司。

## 文件展平与补充资质

- 展平顺序：资质目录保持 `input.json.qualifications` 顺序，每个目录内保持 `files` 顺序。
- 同一资质目录存在多张文件时，每张文件占用独立上传表单，但复用该目录的举证链接。
- 补充资质表单数量严格等于该业务总文件数减一。
- 每次添加补充资质后重新扫描序号和容器，禁止复用旧 DOM。
- 上传与举证链接操作必须限定在当前业务、当前主资质或补充资质容器内。

## 自动保存与发起审核

- 上传一张文件后等待该操作触发的 `submitlice`，仅 HTTP 200 且 JSON `status == 0` 视为成功。
- 举证链接非空时填写并移出输入框，等待另一次 `submitlice` HTTP 200 且 JSON `status == 0`，再回读值一致；空链接不触发填写或等待。
- 新版不填写或验证资质编号、资质名称、有效期/永久。
- 不把页面“待保存”文字或弹窗关闭单独视为成功。
- 最终审核前验证页面业务集合、每个业务上传表单数量、每个表单唯一文件及所有保存响应均与完整输入一致。
- 最终提交关闭时停在填写完成状态；开启时点击底部唯一“发起审核”，并在“确认发起审核？”弹窗中点击唯一“确定”，等待 `submitall` HTTP 200 且 `status == 0`。

## 待真实页面确认事项

## 实现阶段

1. 新版详情页与新增业务资质页识别。
2. 精确点击“新增资质”和蓝色“新增业务资质”。
3. 扫描业务1–4，从后向前删除默认业务2–4。
4. 校验输入中“推广审查”存在且唯一，并处理业务1全部文件。
5. 为其余输入类型逐一新增业务、查询并精确选择经营业务。
6. 将每种类型的所有文件展平为主资质和补充资质表单。
7. 逐文件上传、填写举证链接并验证每次 `submitlice`。
8. 验证最终业务集合、表单数量、文件和链接。
9. 根据最终提交开关决定是否发起审核，并校验 `submitall` HTTP 200 且 `status == 0`。
10. 所有上传、补充资质和举证链接定位限定在当前业务卡片；不得依赖全页面可见控件集合。
11. 执行默认业务删除前，从业务1对应内容容器读取并确认经营业务为“推广审查”。
12. 下拉查询等待异步候选稳定出现，再执行唯一精确选择。
13. 新版执行结果以资质目录标识参与幂等匹配，支持同类型下多个缺省编号/名称的资质目录。
14. 文件上传允许定位隐藏的原生 `input[type=file]`，但其业务容器必须可见且唯一。
15. 业务根容器必须同时覆盖主表单和补充资质操作区，不以包含任意输入框的最小祖先作为最终范围。
16. 推广审查通过明确的经营业务字段或展示值确认，不使用业务卡内任意同名说明文字。
17. 已完成结果匹配必须包含举证链接等完整输入指纹；修改举证链接后不得跳过。
18. 默认业务删除只接受明确的关闭/删除语义控件，不点击任意 SVG。
19. 最终送审前重新扫描业务集合和各业务表单，并将页面表单与本次严格匹配的逐文件保存凭据、举证链接逐项核对。
20. `submitlice` 与 `submitall` 响应只接受 `https://fkzhunru.baidu.com` 上对应精确路径的 POST 请求，禁止仅按 URL 子串归属响应。
21. 缺少完整 `input_fingerprint` 的历史结果不具备安全跳过条件，必须重新处理。

# 任务 6：经营业务清理与资质批量提交开发计划

## 状态

已实现并完成代码审查修复，包含本地 HTML + 无头 Chrome 的 Playwright 页面测试。当前资质策略为整类覆盖：允许编号重复，删除所有可删除旧卡，以 JSON 第一条更新不可删除首卡，其余重新新增。

## 目标

在流程 5 已经打开“行业资质”区域后：

1. 读取公司目录下已校验的 `input.json`。
2. 将 `qualificationTypes[].typeName` 映射到页面“经营业务”。
3. 先处理页面已经存在且输入需要的经营业务：删除所有可删除旧资质，用 JSON 第一条覆盖不可删除首卡，其余全部新增。
4. 删除页面中不需要且允许删除的经营业务，只保留输入需要的类型和系统强制保留类型。
5. 对页面默认不存在的输入类型，在“经营业务”下拉框中精确搜索并添加。
6. 对新增类型，按 `input.json` 顺序提交该类型下的全部资质。
7. 上传资质文件后，无论 OCR 是否成功，都以 `input.json` 字段覆盖页面表单。
8. 验证每个资质卡片创建或更新成功，并输出可恢复的执行结果。
9. 所有资质集合验证成功后，点击“本模块提交/全部提交”并校验 `submitall`。

## 范围

本任务包含：

- 经营业务识别、映射、预检和多余类型删除。
- 页面缺失经营业务的精确搜索和添加。
- 经营业务折叠面板展开。
- 已有资质卡片扫描。
- 保留经营业务下所有可删除旧资质的清理。
- 新增“备用资质”或编辑已有资质。
- 图片/PDF上传。
- OCR 提示弹窗处理。
- 资质编号、名称、有效期、永久选项和举证链接填写。
- 单个资质表单“提交”。
- 提交结果、页面卡片和接口响应验证。
- 执行结果记录、失败恢复和重复运行整类覆盖保护。
- 页面级最终提交及成功响应校验。

本任务暂不包含：

- 删除或替换“主体资质”。
- 自动处理账号、验证码或短信验证。
- 在类型映射不明确时进行模糊删除。

## 前置条件

- 流程 1 已生成有效的 `input/公司名/input.json`。
- 流程 5 已匹配目标 URL、点击“查看”，并确认“行业资质”区域出现。
- 当前浏览器上下文保持登录。
- 每个资质文件已在流程 1 校验：格式为 jpg/jpeg/png/pdf、最多 9 个、单文件不超过 10MB。
- 输入类型均存在已确认的页面显示名或搜索候选映射。

## 输入

每个公司从 `input.json` 使用：

```json
{
  "companyName": "公司名称",
  "url": "https://example.com",
  "qualificationTypes": [
    {
      "typeName": "推广审查",
      "qualifications": [
        {
          "indexName": "资质1",
          "qualificationNo": "资质编号",
          "qualificationName": "资质名称",
          "expiry": {
            "permanent": false,
            "date": "2026-11-12"
          },
          "evidenceUrl": "https://example.com/evidence",
          "files": [
            "推广审查/资质1/证明.jpg"
          ]
        }
      ]
    }
  ]
}
```

资质文件路径相对于 `input.json` 所在的公司目录解析。

## 类型映射

类型映射单独维护在 [type-mapping.md](./type-mapping.md)。

匹配规则：

1. 去除页面前缀 `经营业务N：` 和首尾空白。
2. 使用显式别名映射，不使用包含关系直接执行删除。
3. 页面括号和方括号中的限制说明属于展示名称的一部分，但可以在已登记别名中规范化。
4. 输入类型无法唯一映射到现有面板或下拉候选项时，在任何删除、添加或提交前停止。
5. 多个输入类型映射到同一个页面类型时视为配置错误。
6. 页面存在未知且可删除类型时，只有预检确认它不在目标集合后才删除。
7. “推广审查”等页面标记为不可删除的系统类型，即使输入缺失也只能保留并记录，不能强行操作。
8. “一类医疗器械”和“入驻商城类”是不同经营业务，不得互相映射。

## 总体执行状态机

```text
读取 input.json
      ↓
只读扫描页面经营业务和资质卡片
      ↓
生成并校验执行计划
      ↓
处理页面已存在的目标经营业务资质
      ↓
删除明确的多余经营业务
      ↓
搜索并添加页面缺失的目标经营业务
      ↓
处理新增经营业务资质
      ↓
写入脱敏执行结果
```

### 阶段 A：只读预检

在进行任何删除或提交前完成：

1. 读取并校验 `input.json`。
2. 扫描“行业资质”下全部经营业务面板。
3. 提取页面显示名称、是否可删除、当前序号和展开状态。
4. 使用类型映射表计算：
   - `requiredTypes`：输入需要的页面类型。
   - `existingRequiredTypes`：页面已经存在且输入需要的类型。
   - `mandatoryTypes`：系统强制保留类型。
   - `deleteTypes`：页面存在、输入不需要且允许删除的类型。
   - `addTypes`：输入需要、页面不存在、需要从下拉框搜索添加的类型。
   - `unknownTypes`：无法规范化的页面类型。
5. 对每个 `existingRequiredTypes` 生成整类覆盖计划：所有可删除已填卡加入删除清单；唯一不可删除首卡加入编辑覆盖清单；无法读取编号或存在多个不可删除已填卡时停止。
6. 对 `addTypes` 只读检查“经营业务”下拉框，确认每个类型均有唯一精确候选项；检查过程中不点击“添加”。
7. 任一输入类型映射待确认、重复，或缺失唯一候选项时，停止并输出预检错误。
8. 输出脱敏执行计划；支持后续增加 `--dry-run` 只预览不修改页面。

### 阶段 B：处理页面已存在的目标类型

1. 按 `input.json.qualificationTypes` 原顺序筛选 `existingRequiredTypes`。
2. 展开每个已存在的目标经营业务。
3. 按“阶段 E”的统一资质提交逻辑，处理该类型下的全部资质。
4. 每个类型处理结束后重新扫描页面，并记录成功和失败项。
5. 任一资质失败后立即停止当前公司并输出原始错误；后续备用资质依赖上一张卡片稳定出现，不允许带着未确认状态继续。

### 阶段 C：删除多余经营业务

1. 按页面从后往前删除 `deleteTypes`，避免删除后“经营业务N”重新编号影响定位。
2. 每次通过经营业务容器内部的名称和“删除业务”按钮定位，禁止按全局序号直接删除。
3. 如出现确认弹窗，核对弹窗中的业务名称后确认。
4. 每删除一项，重新扫描页面经营业务列表。
5. 验证被删除类型消失、目标类型仍全部存在。
6. 页面标记不可删除、无删除按钮或名称不一致时立即停止删除阶段。

删除属于不可逆页面变更，必须使用精确映射；未知类型不能猜测删除。

### 阶段 D：搜索并添加缺失经营业务

对预检得到的 `addTypes` 按 `input.json.qualificationTypes` 原顺序处理：

1. 点击“经营业务”下拉框。
2. 在下拉框的搜索输入中填写输入类型名，例如“一类医疗器械”。
3. 等待候选列表加载，只接受映射表中登记页面名称的唯一精确候选项。
4. 选择候选项，回读选择框显示值，确认没有选错。
5. 点击选择框旁的“添加”按钮。
6. 等待新经营业务面板出现并重新扫描全部经营业务。
7. 验证：
   - 新增类型唯一存在；
   - 页面完整显示名与映射一致；
   - 已处理和强制保留类型仍然存在；
   - 页面没有出现重复类型。
8. 添加失败、无候选、候选不唯一或新增后名称不一致时，停止当前公司。
9. 添加成功后立即按“阶段 E”处理该新增类型下的全部输入资质。

禁止通过键盘盲选第一个候选项，也禁止使用部分文本匹配添加。

### 阶段 E：逐类型提交资质

阶段 B 和阶段 D 均复用本逻辑。对目标经营业务中的输入资质按原顺序处理：

1. 定位对应经营业务面板并展开。
2. 扫描当前面板内所有资质卡片，提取：
   - 卡片标题；
   - 资质编号；
   - 资质名称；
   - 有效期；
   - 举证链接；
   - 状态；
   - 编辑/删除入口；
   - 已展示文件数量。
3. 以输入资质编号集合为目标状态，对页面卡片分类：
   - `matchedCards`：资质编号存在于输入中。
   - `extraCards`：已有资质编号，但不在输入中。
   - `emptyRequiredCards`：没有资质编号的系统必填占位卡。
4. 先删除全部 `extraCards`：
   - 从页面靠后的卡片向前删除，避免卡片顺序变化造成误点。
   - 只点击当前经营业务容器内、目标卡片上的删除入口。
   - 如有确认弹窗，核对资质编号后再确认。
   - 每删除一张卡片后重新扫描当前经营业务。
   - 删除完成后验证所有可删除已填资质均已消失。
   - 删除确认信息不一致或删除后仍存在时，停止当前经营业务并记录失败。
   - 唯一不可删除的首张已填卡或空白卡保留。
5. 按 input.json 原顺序覆盖提交：
   - 第一条资质：存在不可删除首卡时编辑覆盖该卡，否则创建新资质。
   - 后续资质：一律通过“上传备用资质文件”创建新资质。
   - 即使页面原内容与 JSON 完全一致，也不跳过。
   - 存在多个不可删除首卡时停止当前经营业务，禁止猜测。
   - 提交后至少比较资质编号、资质名称、有效期/永久、举证链接及页面文件数量；上传接口的服务端文件标识单独记录用于审计。
6. 新增资质时：
   - 如果存在空的系统必填资质占位卡，优先点击该卡编辑入口。
   - 否则点击当前经营业务内“上传备用资质文件”。
   - 等待动态标题为“备用资质N”的可见弹窗。
7. 完成文件上传、OCR处理、字段填写和提交。
8. 弹窗关闭后重新扫描卡片，验证对应“资质编号 + 资质名称”联合键唯一出现。
9. 类型处理结束时验证页面中资质联合键的多重集合与 `input.json` 完全一致。
10. 继续下一条资质和下一种经营业务。

## 文件上传

1. 在当前可见资质弹窗内部定位隐藏的文件 `<input type="file">`，不能点击其他经营业务的上传入口。
2. 将 `input.json.files` 相对公司目录解析为绝对路径。
3. 保持 JSON 文件顺序，使用 Playwright `set_input_files` 上传全部文件。
4. 如果页面上传控件不支持一次多文件，则按顺序逐个上传。
5. 等待每个文件上传完成，验证预览缩略图或文件项数量等于输入数量。
6. 可监听 `POST /permit/web/permit/savelicepic`：
   - HTTP 成功；
   - 响应 `status == 0`；
   - 返回服务端文件名。
7. 上传失败时最多重试当前文件；不得重复提交已成功上传的整组文件。

## OCR 弹窗处理

上传首个文件后，页面可能：

- 自动识别并填写字段；
- 弹出“OCR未识别到数据，请补充资质信息”；
- 不弹窗但异步修改表单值。

统一处理：

1. 上传后等待“文件预览完成”和“OCR提示/表单可编辑”中的任一状态。
2. 如出现 OCR 提示，点击当前最上层提示框中的“好的”。
3. 不依赖 OCR 识别结果，不因识别失败中止。
4. OCR 流程结束后，始终清空并重新填写所有业务字段。
5. 填写完成后再次读取控件值，确保 OCR 的延迟回写没有覆盖输入值。

## 表单字段填写

只在当前可见资质弹窗内部操作：

| input.json 字段 | 页面字段 | 规则 |
| --- | --- | --- |
| `qualificationNo` | 资质编号 | 清空后完整填写，提交前回读 |
| `qualificationName` | 资质名称 | 清空后完整填写，提交前回读 |
| `expiry.permanent=true` | 永久 | 勾选“永久”，确认日期输入为空/禁用 |
| `expiry.date` | 有效期至 | 取消“永久”，直接粘贴 `YYYY-MM-DD` 并回读；禁止使用日期选择面板 |
| `evidenceUrl` | 举证链接 | 非空则填写；为空则清空 |
| `files` | 上传资质文件 | 全部上传并校验数量 |

日期字段先聚焦并全选原值，再用键盘文本插入模拟粘贴，随后失焦触发表单更新。控件拦截键盘事件时，可直接设置输入值并触发 `input/change/blur`；任何情况下都不点击日期选择面板。

## 单个资质提交和验证

1. 提交前构建字段快照并回读核对。
2. 点击当前资质弹窗的“提交”。
3. 监听 `POST /permit/web/permit/submitlice` 作为辅助验证：
   - HTTP 成功；
   - 响应 `status == 0`；
   - 不在日志中输出 Token 或完整请求体。
4. 等待资质弹窗关闭。
5. 重新定位经营业务面板和卡片。
6. 按“资质编号 + 资质名称”验证：
   - 卡片唯一存在；
   - 编号、名称、有效期、举证链接与输入一致；
   - 文件缩略图数量符合预期；
   - 状态为“待提交”或页面认可的成功状态。
7. 任一验证失败，记录当前资质失败；页面仍稳定时继续下一条资质。

## 幂等和断点恢复

- 唯一键使用：`公司 + URL + 页面经营业务规范名 + qualificationNo + qualificationName`。
- 重复执行时仍执行整类覆盖：可删除卡全部删除，不可删除首卡编辑覆盖，其余重新新增。
- 页面已有内容一致也不跳过，确保最终文件和字段完全来自本次 input.json。
- 每条资质完成后立即写入执行结果，程序中断后可从未完成项继续。
- 执行结果继续记录服务端文件标识和输入文件 SHA-256，用于审计和提交后校验，不用于跳过本次覆盖。
- 建议结果文件：

  ```text
  input/公司名/qualification-submit-result.json
  ```

- 结果只记录类型、资质编号、状态、时间、错误摘要和文件数量，不记录 Cookie、Token 或完整动态资质链接。

## 错误分级

### 必须停止整个公司的错误

- 类型映射待确认、重复，或缺失类型无法找到唯一搜索候选项。
- 添加经营业务失败或新增后页面名称不一致。
- 删除目标无法精确定位。
- 登录失效。
- 页面离开目标 URL/行业资质区域。
- 当前 DOM 无法确定操作属于哪个经营业务。
- 可删除旧资质无法被安全定位或删除。

### 记录后继续下一资质的错误

- 单个文件上传失败。
- OCR提示无法关闭。
- 单个表单字段无法填写或回读不一致。
- 单个资质提交接口业务失败。
- 提交后卡片验证失败。

公司结束时，只要存在任何资质失败，整体结果必须为失败，不能调用最终 `submitall`。
所有资质成功且最终集合一致时，必须调用最终 `submitall`；接口失败则公司整体失败。

## 模块建议

```text
src/
├── type_mapping.py              # 类型规范化和显式映射
├── industry_qualification.py   # 经营业务扫描、搜索添加、删除、面板操作
├── qualification_form.py       # 上传、OCR、字段填写和弹窗提交
├── submission_result.py        # 幂等状态和结果文件
└── workflow.py                 # 串联流程 1-6
```

页面对象建议：

- `IndustryQualificationSection`
- `BusinessPanel`
- `QualificationCard`
- `QualificationDialog`

所有定位必须以当前“行业资质”区域、经营业务面板或可见弹窗为作用域，避免全局同名按钮误点。

## 开发顺序

1. 实现类型规范化、映射配置和预检数据模型。
2. 实现经营业务及下拉候选项的只读扫描和执行计划输出。
3. 实现现有目标业务的展开、资质卡片解析和编号查重。
4. 实现多余业务删除及删除后重新扫描。
5. 实现缺失业务的精确搜索、添加和添加后校验。
6. 实现弹窗打开、文件上传和上传响应监听。
7. 实现 OCR 弹窗处理。
8. 实现字段填写、回读校验和永久/日期切换。
9. 实现单个资质提交、卡片验证。
10. 实现幂等、结果文件和断点恢复。
11. 接入现有 `WorkflowRunner`，在流程 5 成功后执行。
12. 使用模拟页面完成自动测试。
13. 使用真实页面先做一条资质的受控验收，再扩展到现有类型、缺失类型和多类型。

## 验收标准

- 类型映射不完整时不执行任何删除或提交。
- 页面多余且可删除的经营业务被准确删除。
- 所有输入需要的经营业务均保留。
- 页面默认缺失的输入类型可通过下拉框唯一搜索并成功添加。
- “一类医疗器械”不会被错误映射或添加为“入驻商城类”。
- 不可删除的系统类型不会被误操作。
- 每个保留经营业务下，所有可删除旧资质均被删除。
- 每个类型的不可删除首卡被 JSON 第一条编辑覆盖，所有可删除卡先删除，其余 JSON 资质重新新增。
- 每个输入类型下的全部资质都被创建或正确更新。
- OCR 成功或失败都不会改变最终提交字段。
- 永久和日期有效期均正确。
- 空举证链接会清空页面字段。
- 每个资质文件全部上传且数量正确。
- 重复运行后页面资质集合仍与本次 input.json 完全一致。
- 单项失败有明确记录，并可从失败项继续。
- 全部资质成功后触发 `submitall`，接口返回 `status == 0` 才算完整成功。

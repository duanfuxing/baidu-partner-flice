# 保存后页面稳定判断修复

目标：处理 Windows 偶发 submitlice 已成功，但“保存后页面刷新稳定”等待超时的问题。
范围：新版保存后的页面一致性等待、阶段日志及本地 Chrome 回归。
依据：用户日志表明失败发生在保存响应校验通过之后；现有实现硬性等待“已保存待送审”并扫描整个业务的 loading，无法区分文字未更新、其他卡片 loading 和真实回填失败。具体 Windows 页面卡点仍需修复后的诊断日志验证。
设计：只在保存响应及请求文件/举证校验成功后进入等待；有上传凭据时以当前卡片文件身份、图片加载和举证值持续一致为准，不以状态文案作为唯一依据；仍等待当前卡片和其祖先的加载遮罩。兼容没有预览凭据的页面保留状态校验。卡片临时消失不得提前通过。记录脱敏的等待原因和超时详情，不重传、不重新保存。
步骤：建立夹具复现；实现稳定条件和日志；执行保存与新版上传回归；记录验收和限制。
依赖：任务 43、53；现有 Playwright 和 pytest，无新增依赖。
验收：状态文字未刷新及相邻卡片 loading 不造成误超时；当前卡片/父级 loading、丢失文件、错误文件、举证不一致及卡片消失不能通过；延迟回填和卡片重建可恢复；失败不操作下一文件；保存失败仍停止。
不在范围：真实公司上传、最终审核、打包发布、变更文件与卡片组织规则。
状态：本地实现及回归完成，未打包发布。

验收结果：原逻辑的相邻卡片 loading 误超时已由本地 Chrome 夹具复现；修复后所有验收项通过。两轮测试分别45项、50项通过（14项重叠，共81个不同场景），包括18项保存稳定性场景及32项新版页面流程。compileall、git diff --check通过。
环境限制：未操作真实公司、未运行真实 submitall；没有 Windows 真机重现数据，不能确定用户该次超时究竟是状态文案还是加载遮罩所致。需安装修复后的 Windows 版本复测，必要时根据新增的具体等待原因继续定位。
